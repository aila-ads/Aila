# Runbook: `User.authUserId` migration on databases with existing users

## The problem

Migration `prisma/migrations/20261003034354_add_supabase_auth_identity` adds
`"User"."authUserId"` as `TEXT NOT NULL` with no default, plus a unique index.

- On an **empty** `User` table (fresh database), it applies cleanly.
- On a database where it **already succeeded**, there is nothing to do.
- On a database that has the init migration **and existing `User` rows** but
  not this migration, it fails with:
  `ERROR: column "authUserId" of relation "User" contains null values`
  and Prisma records it as failed, which blocks every later migration.

## Why the migration file itself is not edited

The migration's header shows it was generated by `prisma migrate dev`, which
also applies it. The live site (ailaxx.com) runs code that writes
`authUserId` when an account is created. So it has very likely been applied
to at least one database already. Editing an applied migration changes its
checksum: `prisma migrate deploy` and `migrate status` ignore that, but
`prisma migrate dev` then reports "modified after it was applied" and asks to
**reset (wipe) the development database**. Leaving the file unchanged avoids
that for every database where it already worked.

A new, later migration cannot help either, because this migration runs (and
fails) first.

So the fix is Prisma's documented "hotfix + resolve" path, used only on the
affected database.

## Step 1: check the database (read-only)

```bash
psql "$DATABASE_URL" -f prisma/manual/authuserid-preflight.sql
```

It prints the migration state (APPLIED / NOT APPLIED / FAILED), the number of
`User` rows, whether Supabase's `auth.users` table is present, and a RESULT:

- `column already present` or `SAFE`: nothing to do. Run
  `pnpm exec prisma migrate deploy` as usual.
- `AT RISK`: continue with Step 2.

## Step 2: apply the safe version manually

Take a backup first.

```bash
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f prisma/manual/authuserid-safe-apply.sql
```

In one transaction, the script:

1. adds `authUserId` as nullable,
2. if `auth.users` exists (Supabase Postgres), links each user to the
   Supabase auth user with the same **confirmed** email (case-insensitive;
   unconfirmed auth users are never linked),
3. stops and rolls back everything if any user is still unlinked,
4. sets `NOT NULL` and creates the unique index `User_authUserId_key`,
   the same end state as the original migration.

If it stops at step 3, decide what to do with the unlinked users (below) and
run it again.

## Step 3: tell Prisma the migration is done

```bash
pnpm exec prisma migrate resolve --applied 20261003034354_add_supabase_auth_identity
pnpm exec prisma migrate deploy
pnpm exec prisma migrate status   # expect "Database schema is up to date!"
```

`migrate resolve --applied` works whether the migration was pending or
recorded as failed.

## Decision: users that cannot be linked

List them with:

```sql
SELECT id, email, "createdAt" FROM "User" WHERE "authUserId" IS NULL;
```

Options:

- **Link manually:** if the person has a Supabase login under another email,
  set `"authUserId"` to that `auth.users.id` (as text).
- **Ask them to confirm:** if a Supabase auth user exists but is unconfirmed,
  confirming the email and re-running the script links them.
- **Delete them:** if they are test or abandoned rows. Some relations use
  `onDelete: Restrict` (for example projects, files, conversations they
  created), so rows that own data must be cleaned up first.
- **Keep them without a login:** this needs a schema change (make
  `authUserId` optional) and code changes, and is not covered here.

## Future migrations

When adding a required column to a table that may contain data, generate the
migration with `prisma migrate dev --create-only` and edit it before applying:
add the column as nullable, backfill, then set `NOT NULL`.
